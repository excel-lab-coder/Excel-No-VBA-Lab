段階3：VBA中級・上級で、Excel内の業務ツールを設計する時期

VBA初級で連続印刷やCSV取込ができるようになると、かなり仕事は楽になります。ただ、そこで終わると「作った本人しか動かせないマクロ」になりがちです。段階3では、VBAを他人が使えるExcel内業務ツールへ育てていきます。

ここで変わるのは、コードの量ではありません。入力、処理、出力、エラー、設定、ログ、引き継ぎまで含めて考えるようになります。

つまり、VBAを「作業を消す道具」として使う段階から、VBAで「Excel内に小さな業務システムを作る」段階へ進みます。

この記事で扱う流れ

  1. 動くマクロから、使い続けられるツールへ
  2. SelectとActivateを卒業する
  3. 配列とDictionaryで処理速度が変わる
  4. 処理を分けると保守できるようになる
  5. エラー処理、ログ、設定シートを持つ
  6. 他人が使うための入力画面とボタン設計
  7. この段階でできるようになること
  8. どれぐらいの人ができるか
  9. この段階の限界

この段階で起きる変化

段階2では、毎月の作業をボタン1つにすることが大きな成果でした。段階3では、もう少し視点が変わります。「自分が動かせるマクロ」ではなく、「他の人も安心して使えるExcelツール」を考えるようになります。

たとえば、連続印刷マクロを作ったとします。自分だけが使うなら、対象シート名や保存先フォルダをコードに直接書いても動きます。しかし他の人が使うなら、対象者の選択、印刷前チェック、保存先の変更、エラー時の表示、処理ログが必要になります。

ここで、VBAは作業短縮から運用設計へ変わります。処理が一度動くことより、毎月安定して動くことのほうが大事になります。

段階3の本質

初級VBAは「自分の作業を消す」段階です。中級・上級VBAは「他人が使っても回る仕組みにする」段階です。

SelectとActivateを卒業する

マクロの記録から入ると、最初はSelectやActivateだらけになります。セルを選んで、コピーして、別のシートを選んで、貼り付ける。記録マクロとしては自然ですが、実務ツールとしては壊れやすくなります。

中級に進むと、画面で選択している場所に頼らず、ブック、シート、範囲を明示して操作するようになります。これだけでコードの安定感がかなり変わります。

' 記録マクロ寄り Sheets("元データ").Select Range("A1:C100").Select Selection.Copy Sheets("出力").Select Range("A1").Select ActiveSheet.Paste ' 中級以降の考え方 Worksheets("元データ").Range("A1:C100").Copy _ Destination:=Worksheets("出力").Range("A1")

この変化は小さく見えますが、かなり重要です。画面を選択しないので速くなりますし、ユーザーが別のシートを開いていても処理が安定します。

ここで初めて、Excelの見た目ではなく、Excelのオブジェクト構造を触っている感覚が出てきます。ブック、シート、範囲、セル、行、列。それぞれを明示的に扱うようになります。

配列とDictionaryで処理速度が変わる

VBA初級では、セルを1つずつ読み書きしがちです。100行なら問題ありませんが、1万行、5万行になると急に重くなります。ここで配列やDictionaryを使うかどうかで、実務レベルがかなり変わります。

配列を使うと、シート上の値を一度メモリに取り込み、処理してからまとめて戻せます。Dictionaryを使うと、重複チェック、集計、マスタ照合、存在確認が速くなります。

Dim data As Variant Dim i As Long data = Worksheets("明細").Range("A2:D50000").Value For i = 1 To UBound(data, 1) If data(i, 2) = "対象" Then data(i, 4) = "出力" End If Next i Worksheets("明細").Range("A2:D50000").Value = data

この段階で画期的なのは、Excelを「セルを触る画面」としてではなく、「データを一度まとめて扱う場所」として見られるようになることです。後のPower Queryやスピル関数にも、この感覚はつながります。

処理を分けると保守できるようになる

初級VBAでは、1つのSubに全部を書きがちです。CSVを開く、整形する、チェックする、印刷する、保存する、メッセージを出す。最初は動きますが、後から直すのが苦しくなります。

中級以降では、処理を役割ごとに分けます。入力を読む処理、データを整える処理、チェックする処理、出力する処理、ログを書く処理。分けておくと、エラーが起きたときに原因を探しやすくなります。

Main ├─ LoadInputFiles ├─ NormalizeData ├─ ValidateData ├─ CreateReports ├─ SaveOutputs └─ WriteLog

この分割は、きれいなコードを書くためだけではありません。業務の説明にも効きます。「何を入力し、どこでチェックし、何を出力しているか」を、コードの構造で表せるようになります。

エラー処理、ログ、設定シートを持つ

他人が使うツールにするなら、正常時だけを考えていては足りません。ファイルがない、列名が違う、保存先フォルダがない、対象データが0件、同じファイル名がすでに存在する。こうしたことは実務では普通に起きます。

中級以降では、エラー処理、チェック処理、ログ出力を考えるようになります。処理開始時刻、処理件数、エラー件数、対象ファイル名、出力先。こうした情報を残すだけで、トラブル時の復旧がかなり楽になります。

設定シート ├─ 入力フォルダ ├─ 出力フォルダ ├─ 対象年月 ├─ 印刷対象区分 └─ 管理者メモ ログシート ├─ 処理日時 ├─ 対象ファイル ├─ 処理件数 ├─ エラー内容 └─ 実行者

設定をコードに埋め込むのではなく、設定シートに逃がす。エラーをMsgBoxだけで終わらせるのではなく、ログに残す。こうした工夫で、作った本人以外でも扱いやすくなります。

他人が使うための入力画面とボタン設計

VBA中級・上級では、ユーザーインターフェースも考えるようになります。ボタンをどこに置くか。押す前に何を確認させるか。処理中に何を表示するか。終わった後に何を伝えるか。

UserFormを使う場合もあります。対象年月を選ぶ、出力先を指定する、処理区分を選ぶ、対象者をチェックする。こうした入力画面を作ると、利用者がシート構造を知らなくても操作できます。

ただし、画面を作ればよいわけではありません。入力項目が多すぎると使われません。確認メッセージが多すぎると押されなくなります。ボタンが多すぎると、どれを押せばよいか分からなくなります。

他人が使うVBAで大事なこと

処理の速さだけではなく、迷わず使えること、間違えにくいこと、失敗したときに戻れることが大事です。

この段階でできるようになること

段階3を通ると、VBAで作れるものの性質が変わります。自分の定型作業を短くするだけでなく、部署の中で使われる小さな業務ツールを作れるようになります。

できること 段階2との違い 現場で効く理由
大量データを高速処理する セル操作から配列処理へ進む データ件数が増えても現実的に動く
設定を外に出す コード修正なしで運用条件を変えられる 担当者変更や月次変更に耐えやすい
ログとエラー処理を持つ 止まった理由を残せる 復旧、問い合わせ、引き継ぎが楽になる
利用者向けの画面を作る 作った本人以外でも操作できる 部署内で使い回しやすくなる

画期的な進化は、VBAが「速く動くコード」から「運用を含んだ仕組み」へ変わることです。この段階を越えると、Excelが小さな業務システムに見えてきます。

どれぐらいの人ができるか

厳密な統計ではなく現場感ですが、この段階までできる人は一般事務の中ではかなり少ないです。マクロの記録や簡単なVBAを触れる人はいても、配列、Dictionary、設定シート、ログ、エラー処理まで含めて業務ツールとして組める人は一気に減ります。

部署内に1人いればかなり強いレベルです。複数部署をまたいで頼られることもあります。Excelが得意な人というより、「業務ツールを作れる人」として見られ始めます。

レベル できること 現場での人数感
VBA初級 記録マクロ、連続印刷、簡単なCSV取込 Excelが強い職場なら見かける
VBA中級 最終行、ループ、配列、処理分割、設定シート 部署に1人いるとかなり助かる
VBA上級寄り ログ、エラー処理、Dictionary、UserForm、運用設計 一般事務ではかなり希少

ここまで来ると、単に自分の作業が速いだけではありません。周りの作業の仕組みを変えられます。だから強い一方で、依頼が集まりやすく、作ったツールの保守も背負いやすくなります。

ツール職人の孤独と「Excelの檻」への絶望

VBA中級・上級になり、配列やDictionary、ログ出力、エラーハンドリングを覚えると、Excel内に立派な業務システムを構築できるようになります。周りからの評価も高く、部署の基幹業務をあなたのツールが支えている状態になります。

しかし、ここでも新たな絶望が待っています。それは「Excelという檻」の限界です。データは社内のWebシステムから手でダウンロードしなければならない。結果は別の基幹システムに手入力しなければならない。どんなにExcelの中で処理を高速化しても、その前後の「システム間の手渡し」は人間の手作業のままです。

また、ツールの規模が大きくなるにつれ、「本当にExcelで作るべきだったのか？」という根本的な疑問も湧いてきます。便利だからこそ依頼が増え、保守も増え、作った本人へ責任が集中します。

段階3の壁：Excel内完結の限界と野良システム化

Excelの内部をどれだけ完璧に設計しても、前後の業務フローが手作業である限り、真の自動化は達成できません。ここでExcelの外側を動かしたい欲求が生まれます。

この段階を通過したサイン

  • Select/Activateを使わずにブック・シート・範囲を直接操作できる
  • 配列にデータを取り込んでまとめて処理できる
  • Dictionaryで高速な照合・集計ができる
  • 処理をSub/Functionに分割して設計できる
  • エラー処理、ログ出力、設定シートを組み込める
  • UserFormやボタン配置で、他人が迷わず使える入口を作れる
  • Excel内は整ったが、外部システムとの手作業に強いストレスを感じている

まとめ

段階3は、VBA初級の「動くマクロ」から、Excel内の業務ツールを設計する段階です。

SelectやActivateを卒業し、配列やDictionaryで処理速度を上げ、処理を分け、エラー処理、ログ、設定シート、入力画面まで考える。ここまで来ると、Excelは単なる作業ファイルではなく、小さな業務システムになります。

ただし、Excel内で作れるようになるほど、次はExcelの外側も動かしたくなります。Web画面、外部アプリ、PDF、メール、社内システム。ここから次の段階、VBA応用による外部連携へ進みます。
